# 13. ほかのターミナルとどこで差をつけるか（Positioning）

2026-10-12 の調査のまとめ。数字と出典は調べた時点のもの。出典のない推測は「推測」と書く。

## 1. いまのターミナル

| | 対応 OS | 描画 | 特徴 | 弱いところ |
| --- | --- | --- | --- | --- |
| Windows Terminal | Windows | DirectX | Windows の標準。設定画面、UIA によるスクリーンリーダー対応 | 1.18 の打鍵遅延 66.7 ms（Austin 2024）、待機中の CPU が高い。デタッチなし |
| WezTerm | 3 OS | OpenGL / WebGPU | Lua で何でも書ける。マルチプレクサ内蔵 | 最後のタグ付きリリースが 2024-02。遅延 66.7 ms（同上） |
| Alacritty | 3 OS | OpenGL | 最小・速い | タブも分割も合字もない（tmux 前提） |
| kitty | macOS / Linux | OpenGL | 画像とキーボードのプロトコルの元祖。解析 134 MB/s（自社計測） | Windows なし |
| Ghostty | macOS / Linux | Metal / OpenGL | ネイティブ UI、速い、作りが丁寧 | Windows は「予定なし」（1.3.0 のリリースノート）。プラグインなし。セッションの保存は直前の 1 回だけ |
| iTerm2 | macOS | Metal | tmux -CC、トリガー、Python API | macOS だけ |
| Warp | 3 OS | 自前 | ブロック UI、AI | ログイン必須（2024-11 に撤回）、テレメトリ、独自の入力欄がシェルの挙動を変える |
| Wave / Tabby / Hyper | 3 OS | Electron | ウィジェット、プラグイン | 重い。プラグインに権限の仕組みがない |
| foot | Linux（Wayland） | CPU | 遅延が小さい、サーバーモード | Wayland だけ |

出典: kitty の performance ページ、Chad Austin「Windows Terminal latency」（2024-02）、Ghostty 1.3.0 リリースノートと discussion #2480、WezTerm のリリース一覧、Warp のブログ（ログインとテレメトリ）。

## 2. ターミナルの「あたりまえ」

使う人が最初の 5 分で確かめ、欠けていれば戻ってこないもの。

- キーを押してから文字が出るまでが短いこと。大量出力の最中でも Ctrl+C がすぐ効くこと
- 24 ビット色、太字・斜体・下線、波線と色つき下線（Neovim の診断）
- 代替画面、スクロール領域、ブラケットペースト、フォーカス通知、SGR マウス、同期出力（DEC 2026）
- OSC 52 / 8 / 7 / 133、Kitty キーボードプロトコル
- Unicode の幅、書記素クラスタ、絵文字の ZWJ、結合文字、リサイズ時の再折り返し
- フォントのフォールバック（CJK、Nerd Font）、合字の切り替え、HiDPI
- IME: 変換中の文字がカーソルの位置に出て、候補ウィンドウがその近くに出ること
- スクロールバックの検索、タブと分割、ちゃんと動くコピーと貼り付け
- ログイン不要、テレメトリなし、AI は使うと決めた人だけ

一週間以内に求められるもの: URL のヒント、キーボードだけでの選択、セッションの復元、コマンドパレット、プロンプト単位の移動、コマンド終了の通知、画像、プロファイル。

## 3. なぜターミナルで作業するのか

よく挙がる順（HN や掲示板の議論、ICSE 2022 の論文からのまとめ。数えた順位ではない）。

1. 組み合わせられる・自動化できる（テキストでつながる）
2. 速さとキーボードだけで済むこと
3. リモート（SSH）と、GUI が固まったときの逃げ道
4. 何が起きたかが文字で残る、隠れた処理がない
5. 同じことをもう一度できる（コマンドは保存して共有できる）
6. 覚えたことが長く使える（Stack Overflow 2025 で Bash/Shell は全回答者の 48.7%）

2025〜2026 年は、AI のコーディングエージェントが動く場所としてもターミナルが使われている。

離れる理由として一番はっきりしているのは、ログインの強制とテレメトリ（Warp 自身が「数百人の開発者が使えなかった」と書いた）。AI は「頼んだときに、何を送るか見せて、実行前に聞く」なら受け入れられ、「最初から入っている」「出力をクラウドに送る」と嫌われる（Stack Overflow 2025: AI を高く信頼する人は 3%）。

初心者が怖がるのは、何が起きているか分からないことと、壊してしまうこと（「黒い画面こわい」）。英語のエラーメッセージも壁になる。日本語の利用者には IME の不具合が繰り返し報告されている（Windows Terminal #13398、iTerm2 や Ghostty で候補ウィンドウが左端に出る問題など）。

## 4. 誰も埋めていないところ

調べた範囲で、どのターミナルも満たしていないもの。

1. **ウィンドウより長生きするシェル**。tmux なしで、アプリが落ちても更新しても、シェルとスクロールバックが残る。Windows には tmux がない。WezTerm のマルチプレクサは保守が止まりがちで、Contour のデーモンは実験段階、Ghostty は直前のセッションを開き直すだけ
2. **Windows での品質**。Ghostty は Windows を出さない。kitty もない。Windows Terminal は遅延と待機中の CPU に課題がある
3. **日本語入力**。IME の位置と確定の扱いは、どのターミナルでも壊れやすい
4. **正直な性能の数字**。公開されている比較は古いか、作者自身が測ったもの。遅延を負荷中に測った例、スクロールバック 1 行あたりのメモリ、起動時間はほとんど公開されていない
5. **安全に足せる拡張**。Hyper、Tabby、Wave のプラグインは全権限で動く。WezTerm の Lua もサンドボックスなし。Ghostty には拡張がない

## 5. otterm の差のつけ方

### 5.1 シェルはウィンドウより長生きする（判断 M26、1.2 で実装）

シェルは別プロセスのセッションデーモンで動く。ウィンドウが落ちても、更新や設定の反映で再起動しても、シェルとスクロールバックはそのまま残り、次のウィンドウがつなぎ直す。普通に閉じたときは今までどおり終わる（`general.keep_sessions = "always"` で閉じても残す）。Windows でも tmux なしで動く。

これは見た目ではなく作りの違いで、ほかのターミナルが後から真似しにくい。PTY と VT の状態を最初からウィンドウと分けて設計してあったので（`SessionManager` trait、判断 C14）、otterm は置き換えられた。

### 5.2 何も足していない状態から始め、権限つきの mod で足す（判断 M25）

入れたばかりは普通のターミナル。足すものは自分で選ぶ。mod は権限を宣言し、サンドボックスで動く。

### 5.3 日本語を最初から正しく

IME、全角幅、曖昧幅の設定、日本語の UI と辞書。不具合は後回しにしない。

### 5.4 数字は自分で測って、測り方ごと出す

打鍵遅延、スループット、メモリ、起動時間を、測り方と一緒に `docs/bench/` に載せる。勝っていないところも書く。

### 5.5 AI は道具として

最初はオフ。使うときは、どこに何を送るかを毎回見せる。答えはコツメの言葉にしない（「AI の回答」）。実行は必ず人が Enter を押す。

## 6. 見た目と言葉

AI が作ったように見えるもの（見出しごとの絵文字、きらきらのアイコン、グラデーション、すりガラス、同じ形の箇条書き、誇張した宣伝文句）は使わない。言葉は具体的に、できないことは正直に書く。コツメは短く、自分が見たことだけを話す。詳しくは [12-design-system.md](12-design-system.md) と、各画面の文言。

## 7. 残っている課題（性能）

2026-10-12 の計測（Ryzen 7 3700X、release）。

| 項目 | 値 | 対応 |
| --- | --- | --- |
| VT 解析（スクロールする ASCII） | 約 33 MiB/s → 1.2 で 70〜80 MiB/s | 済み: 圧縮を別スレッドへ、ASCII の連続をまとめて書く、全画面スクロールを回転で |
| Windows の PTY | 29〜35 MiB/s（同梱の OpenConsole） | どの Windows のターミナルも同じ上限 |
| フレームの作成 | 200×60 の全体で約 0.24 ms | 十分 |
| スクロールバック 100 万行 | 約 155 MiB（1 行 157〜165 B） | 十分 |
| 打鍵遅延（描画まで、Canvas） | p50 1.8 ms、p99 7.6 ms | 画面に出るまでの実測（カメラ）が未 |

Linux と macOS では PTY が 100 MB/s 以上出るので、VT の解析を速くしないと otterm 自身が上限になる。
