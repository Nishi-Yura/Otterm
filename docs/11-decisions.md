# 11. 判断一覧（Decision Log）

実装前に決めておくべき事項を、分野ごとに番号付きで列挙する。

**A〜L の全項目は 2026-10-10 に推奨どおり決定した。** 決定内容は各仕様書に反映済み（反映先は「影響」欄）。新しい未決事項が出たら M 章以降に追記する。
各項目は「選択肢」「推奨」「影響するドキュメント」「時期」を持つ。決まったものは `決定:` を書き足し、根拠を 1 行残す。

時期の意味:

- **仕様** … 仕様書を細部まで詰めるために今決める
- **M0** … 実装着手（M0）までに決める
- **M3** … mod 基盤（M3）までに決める
- **後** … v1.0 公開までのどこかで決めればよい

## B. 製品の核となる UX

### B1. 入力欄の形
- 選択肢: **(a)** シェル自身の行編集をそのまま使い、otterm は上に支援 UI を重ねる / **(b)** Warp のように otterm 独自の入力ボックスを持ち、確定時にシェルへ送る
- 決定（2026-10-10、推奨どおり）: **(a)**。「普通のターミナルとして動く」を守れる。vim や fzf など対話的なツールとの相性も崩れない。(b) は補完や説明の精度が上がるが、シェルのキーバインドやプラグイン（zsh-autosuggestions 等）が死ぬ。複数行エディタ（Shift+Enter）のときだけ一時的に (b) に切り替える
- 影響: 03、02 §6
- 時期: 仕様

### B2. ブロックの表示スタイル
- 選択肢: **(a)** 従来通り連続したテキストに細いガターで区切りを示す / **(b)** Warp のようにブロックごとにカード化して余白と枠を付ける
- 決定（2026-10-10、推奨どおり）: **(a)** を既定、(b) はレイアウトプリセット `cards` として用意。(a) なら tmux や TUI と見た目が衝突しない
- 影響: 03 §6、04
- 時期: 仕様

### B3. Tab キーの扱い
- 選択肢: 常にシェルへ渡す / 常に otterm が奪う / ガイドレベルで切り替え
- 決定（2026-10-10、推奨どおり）: **Lv0〜2 はシェルへ渡し、Lv3 のみ otterm の補完を Tab で確定**。Lv3 の人はシェル補完をまだ知らない。設定で個別に変更可
- 影響: 03 §8.2、06
- 時期: 仕様

### B4. Ctrl+C / Ctrl+V（Windows）
- 選択肢: 常に SIGINT / 選択範囲があればコピー / Ctrl+Shift のみ
- 決定（2026-10-10、推奨どおり）: **Windows は「選択範囲があればコピー、なければ SIGINT」を既定**、macOS と Linux は Ctrl+Shift+C/V 既定。Windows Terminal と同じ振る舞いで混乱が少ない
- 影響: 03 §5、06
- 時期: 仕様

### B5. Ctrl+R を奪うか
- 選択肢: otterm の履歴 UI / シェルの履歴検索のまま
- 決定（2026-10-10、推奨どおり）: **Lv1 以上では奪う**。Lv0 はシェルに渡す。fzf や atuin を使っている人は Lv0 か個別設定で戻せる
- 影響: 03 §8.5、06
- 時期: 仕様

### B6. シェル統合の導入方法の既定
- 選択肢: rc ファイルに 1 行追記（要許可） / 起動引数で注入（ファイルを触らない） / 手動
- 決定（2026-10-10、推奨どおり）: **既定は起動引数注入**。ユーザーのファイルを触らずに済み、他ターミナルから起動したときに干渉しない。rc 追記は「他のターミナルでも otterm の統合を使いたい人」向けのオプトイン。これは 03 §6.2 の現記述と逆なので要修正
- 影響: 03 §6.2、06
- 時期: 仕様

### B7. ガイドレベルの既定とオンボーディングの対応
- 選択肢: 既定 Lv2 / 既定 Lv1
- 決定（2026-10-10、推奨どおり）: オンボーディングの 3 択を「はじめて → Lv3」「たまに使う → Lv2」「毎日使う → Lv1」に対応させる。オンボーディングをスキップした場合は **Lv1**（上級者がスキップしがちなため）
- 影響: 03 §11
- 時期: 仕様

### B8. 危険コマンドの「ゴミ箱に送る」の実装
- 選択肢: 入力欄の `rm ...` を `otterm trash ...` に書き換えて見せる / 裏で otterm が直接ゴミ箱へ移動し、シェルには何も送らない
- 決定（2026-10-10、推奨どおり）: **書き換えて見せる**。「何が実行されたか」が履歴に残り、学習にもなる。`otterm trash` は CLI のサブコマンドとして提供し、単体でも使える
- 影響: 03 §8.3、06 §4
- 時期: 仕様

### B9. 入力中の `--help` 自動取得
- 選択肢: 辞書にないコマンドは入力中に `cmd --help` を裏で実行する / しない（実行後の失敗時のみ）
- 決定（2026-10-10、推奨どおり）: **入力中は実行しない**。未知のコマンドを裏で実行するのは副作用のリスクがある（`--help` を解釈せず動き出すツールがある）。`man` ページと `--help` のキャッシュは「ユーザーがそのコマンドを一度実行した後」に作る
- 影響: 03 §8.1
- 時期: 仕様

### B10. GUI 操作で `cd` をシェルに送るか
- 選択肢: ファイルツリーでフォルダを開くとシェルに `cd` を送る / ツリーだけ移動する
- 決定（2026-10-10、推奨どおり）: **Lv2 以上はシェルに送る**（学習になる）、Lv0〜1 はツリーだけ。ピン留めで常に固定可
- 影響: 03 §9.2
- 時期: 仕様

### B11. エラー助言のインストール提案で使うパッケージマネージャ
- 選択肢: OS 既定のみ（winget / brew / apt） / 検出したものを優先（scoop、choco、dnf、pacman、nix）
- 決定（2026-10-10、推奨どおり）: **検出優先**。`PATH` にあるものを使い、複数あれば候補を並べる
- 影響: 03 §8.4
- 時期: 後

### B12. スクロールバックの既定と無制限
- 選択肢: 10,000 行 / 100,000 行 / 無制限（ディスクスピル）
- 決定（2026-10-10、推奨どおり）: **10,000 行を既定**、無制限は設定で。ディスクスピルの保存先とサイズ上限（既定 1 GB）を決めておく
- 影響: 03 §4、09 §3.7
- 時期: 仕様

### B13. 曖昧幅文字の既定
- 選択肢: 半角 / 全角 / ロケールで自動
- 決定（2026-10-10、推奨どおり）: **半角を既定**、日本語 UI を選んだ人には初回に「全角にしますか？」を聞かない（ほとんどの CLI ツールは半角前提）。設定で変えられることだけ案内

### B14. 同梱フォント
- 選択肢: 同梱しない / Nerd Font の記号フォントだけ同梱 / 等幅フォント一式を同梱
- 決定（2026-10-10、推奨どおり）: **Symbols Nerd Font Mono（記号のみ、OFL）を同梱**してフォールバックに使う。これで「アイコンが四角になる」初心者の躓きが消える。本文フォントは OS 既定を使い、日本語は OS のフォントにフォールバック
- 影響: 04 §3
- 時期: 仕様

### B15. 単一インスタンスと新規ウィンドウ

- 決定（2026-10-10、推奨どおり）: **単一インスタンス、新タブ**（06 に記載済み）。`--new-window` で別窓

### B16. 複数行貼り付けの確認の既定

## C. アーキテクチャ・技術

### C1. UI フレームワーク
- 選択肢: SolidJS / Svelte 5 / Preact / React
- 決定（2026-10-10、推奨どおり）: **SolidJS**。仮想 DOM がなく、宣言的 UI（mod の JSON ツリー）を細粒度に更新しやすい。React は mod 作者には馴染みがあるが、本体 UI の更新コストが高い。mod 側は JSON ツリーなのでフレームワークに依存しない
- 影響: 02
- 時期: M0

### C2. mod 実行環境
- 選択肢: **(a)** Web Worker 内で QuickJS（WASM）を動かす二重サンドボックス / **(b)** Web Worker に直接 JS を読み込み、グローバルを削って使う
- 決定（2026-10-10、推奨どおり）: **(a)**。(b) は Worker のグローバル（`fetch`、`importScripts`、`indexedDB`）を完全には消せず、CPU 時間の制限や強制中断もできない。(a) は mod あたり数 MB のメモリと起動 50 ms 程度のコストがかかるが、「mod が暴走しても本体が落ちない」を保証できる。M3 で実測し、起動コストが問題なら Worker を事前に温めておく
- 実装（2026-10-11）: `quickjs-emscripten-core` + `@jitl/quickjs-singlefile-browser-release-sync`（WASM を JS に埋め込んだ変種。Worker のバンドルは約 760 KB）。mod ごとに Runtime と Context を作り、メモリ上限 64 MB、スタック 1 MB、割り込みハンドラでコールバック 1 回を 5 秒までに制限する。開発機で Git Status Bar の activate は 44 ms（Worker の起動から `activate()` の完了まで）。見積もりどおりなので Worker の事前起動はしない
- 影響: 02 §4.3、05 §4
- 時期: M3

### C3. 文字の整形（シェーピング）をどちらで行うか
- 選択肢: WebView 側で HarfBuzz（WASM） / **Rust 側で rustybuzz + swash**
- 決定（2026-10-10、推奨どおり）: **Rust 側**。グリフ ID と位置まで Rust で決め、WebView は四角形を並べるだけにする。ネイティブレンダラに移行するときに描画以外のコードがそのまま使える。04 §2.3 の「HarfBuzz（WASM）」は要修正
- 実装（2026-10-11）: `otterm-text` クレート。セル（書記素クラスタ）ごとに rustybuzz で整形し、文字をすべて持つ最初のフォントを使う（フォールバック）。絵文字の ZWJ 列や国旗も 1 セルの 1 ビットマップになる。合字（`font.ligatures`、既定オン）は、隣り合う同じ装飾のセルのうち記号（`-=<>!~|&:+*/#?.%$@^\\`）を含む並びを 1 本の文字列として整形し（`text_runs`）、フォントが結合したグリフを先頭のセルから描く。主フォントに全文字があるときだけ結合する。斜体の面に合字がないフォント（Cascadia Code の斜体）では結合しない
- 影響: 02、04 §2.3、09 §3.4
- 時期: M0

### C4. グリフのラスタライズ
- 選択肢: ブラウザの Canvas2D で描いてアトラス化 / Rust（swash）でラスタライズしてテクスチャとして送る
- 決定（2026-10-10、推奨どおり）: **Rust**。3 OS で同じ見た目になり、サブピクセル処理も自前で制御できる。C3 と同じ理由でネイティブ移行が楽
- 実装（2026-10-11）: `otterm-text` が swash でラスタライズし（40 px 未満はヒンティングあり、太字・斜体がないフォントは合成）、`text_glyphs` コマンドがクラスタ単位のビットマップをまとめて返す。UI のアトラス（`packages/ui/src/screen/glyphAtlas.ts`）は足りないグリフを 1 フレーム分まとめて要求し、届いたら行を描き直す。ASCII は先に温めるので打鍵で待たない。グリッドの寸法（`text_metrics`）も Rust のフォント計測に合わせた。Rust が使えない（フォントが 1 つもない）ときだけ WebView の Canvas 2D で描く。輪郭の濃さは文字色の明るさで補正し、明るい背景でも暗い背景でも設計どおりの太さに見せる
- 影響: 02、09
- 時期: M0

### C5. VT コアの実装
- 選択肢: `vte` クレート + 自前グリッド / `alacritty_terminal` を使う / libghostty（FFI）
- 決定（2026-10-10、推奨どおり）: **`vte` + 自前グリッド**（09 §3.5 で暫定決定）。ブロック用の OSC 拡張と画像プロトコルを自由に足せる。M0 で libghostty の状態を確認して記録
- 影響: 02、09
- 時期: M0

### C6. 設定スキーマの定義方法
- 選択肢: JSON Schema を手書き / Rust の型から `schemars` で生成 / 独自 DSL
- 決定（2026-10-10、推奨どおり）: **Rust の型から生成**。設定の型・既定値・説明をコードと一致させる。mod の設定は `otmod.toml` の `[settings.schema]`（JSON Schema のサブセット）で受け取り、同じ形に変換

### M1. mod サンドボックスのタイマー

- 影響: 02 §4.3、05 §5
- 時期: M3

### M2. グリッド差分の転送手段（C13 の見直し）
- 経緯: C13 で「Tauri の生ペイロード IPC を第一候補とし、M0 で WebSocket と比較。差が小さければ単純な方」とした。M0 で測ると差は 10 倍以上あった（[bench/baseline.md](bench/baseline.md) §4.1）。全画面 96 KiB の片道 p99 が Tauri Channel 4.9 ms、WebSocket 0.34 ms。段 4 の予算は 1〜2 ms
- 選択肢:
  - (a) Tauri Channel のまま。差分を小さく保つ工夫（変更行だけ送る、圧縮）で予算に収める
  - (b) **ローカル WebSocket**（127.0.0.1 の空きポート）。起動ごとのトークンで接続を認証し、同じユーザーの別プロセスからの接続も拒む（K6 と同じ考え方）。コマンドと設定は Tauri IPC のまま、グリッド差分と PTY 出力だけを WebSocket に流す
  - (c) カスタム URI スキーム + `fetch` のストリーミング
- 決定（2026-10-11、推奨どおり）: **(b) ローカル WebSocket + 起動ごとのトークン認証**。グリッド差分と PTY 由来のデータだけを流し、コマンドと設定は Tauri IPC のまま
- 推奨の根拠: 全画面の差分でも予算の 1/5 以下に収まり、1 MiB でも p50 1.1 ms。ポートを開くことの危険はトークン認証と 127.0.0.1 限定で抑える。(c) は未計測なので、M1 で同じベンチに足して比べる
- 3 OS の比較（2026-10-11、CI。[bench/baseline.md](bench/baseline.md) §4.4）: 往復 p50 は 3 OS ともすべての大きさで WebSocket が速い。96 KiB で macOS 0.96 → 0.38 ms、Linux 1.98 → 0.64 ms、Windows 4.25 → 0.26 ms。Tauri Channel が予算に収まるのは macOS だけだった
- 影響: 02 §2、09 §3.3、C13
- 時期: M1 の着手前

### M3. Windows の ConPTY のスループット
- 経緯: OS 同梱の ConPTY（conhost）経由だと 8.5 MiB/s しか出ない（[bench/baseline.md](bench/baseline.md) §4.1）。09 の目標「大量出力で Windows Terminal を下回らない」を満たせない。Windows Terminal と WezTerm は Microsoft が MIT で配布している新しい `conpty.dll` と `OpenConsole.exe` を同梱している。portable-pty は実行ファイルと同じフォルダにこの 2 つがあれば自動で使う
- 選択肢: OS 同梱の ConPTY のまま / **`conpty.dll` と `OpenConsole.exe` を同梱**（NuGet の Microsoft.Windows.Console.ConPTY から取得）
- 決定（2026-10-11、推奨どおり）: **`conpty.dll` と `OpenConsole.exe` を同梱**する。バージョンは固定し、更新は ConPTY のリリースを見て手動で上げる
- 推奨の根拠: インストーラに 2 ファイル（数 MB）が増えるだけで、大量出力が約 3 倍速くなる
- 検証（2026-10-11）: 同梱版 1.25.260930003 でスループットが 9.0 → 29 MiB/s（約 3.2 倍）、往復遅延は変わらず（[bench/baseline.md](bench/baseline.md) §4.3）。Windows Terminal との比較は参照マシンで行う
- 影響: 02 §1.2、A9（インストーラ）、09
- 時期: M1

### M4. プロンプトを誰が描くか
- 問題: otterm の中のプロンプト（フォルダ名、Git ブランチなど）は、シェルや Oh My Posh などが文字として描いている。そのため他のターミナルと同じ見た目になり、otterm のテーマや mod では変えられない
- 選択肢: **otterm が UI 部品として描く** / otterm 独自の文字プロンプトをシェルに注入する / シェルのまま
- 決定（2026-10-11、ユーザー決定）: **otterm が UI 部品として描く**。シェル統合（OSC 133 / 7 / 7777）で受け取った CWD、Git ブランチ、終了コード、所要時間を、ブロックの見出し（プロンプトバー）として otterm が描画する。シェル側のプロンプトはフックが最小（`❯` 程度）に差し替える
- 見た目: プロンプトバーの部品（パンくず、ブランチ、終了状態、所要時間）の並び・色・アイコン・枠はテーマで変えられ、mod から部品を足せる
- 既存のプロンプトを使いたい人向けに、設定 `shell.prompt = "otterm" | "shell"`（既定 `otterm`）を用意する。`shell` ではシェルのプロンプトをそのまま表示する
- シェル統合が効かないシェル（cmd など）では、シェルのプロンプトをそのまま表示する
- 試作（2026-10-11）: pwsh のみ。フックが `OSC 7777;bar;<base64 JSON>`（CWD、ホーム、Git ブランチ）と `OSC 7777;done;<終了コード>;<ms>` を送り、端末はバーを行に結び付けて差分で UI に送る。行全体の消去（`cls` など）でバーも消える。Git ブランチは git を起動せず `.git/HEAD` を読む。見た目は `.prompt-header` の CSS とテーマの `prompt-*` キー
- 影響: 03 §6、04、05（UI 拡張点）、06、07 M2
- 時期: M2（pwsh の試作は済み）

### M5. フックスクリプトの置き場所と bash のログインシェル
- 経緯: M2 で bash / zsh / fish のフックを書いた。bash は `--rcfile`、fish は `--init-command`、zsh は `ZDOTDIR` でファイルのパスを渡す必要があり、pwsh のようにインラインでは渡せない。また Git Bash の既定プロファイルは `--login -i` で、ログインシェルの bash は `--rcfile` を無視する
- 選択肢:
  - 置き場所: 一時フォルダに毎回書く / **設定フォルダの `shell-integration/` に書き出す** / インストーラが置く
  - bash のログイン: 統合しない / **`-l` を外して `OTTERM_SHELL_LOGIN=1` を渡し、フックが `/etc/profile` と `~/.bash_profile` → `~/.bash_login` → `~/.profile` の順を再現する**（VS Code と同じやり方）
- 決定（2026-10-11）: **設定フォルダの `shell-integration/`** に、実行ファイルに埋め込んだ内容を初回起動時（中身が変わったときだけ）書き出す。ユーザーが中身を読める場所であり、03 §6.2 の「スクリプトを表示」の実体にもなる。bash のログインシェルは **フック側で再現**する
- 根拠: 一時フォルダは `otterm mod` などから参照しにくく、インストーラ任せだと開発ビルドで動かない。bash の `$BASH_COMMAND` が最初の単純コマンドしか返さない制限は受け入れる（zsh / fish / pwsh は行全体が取れる）
- 影響: 03 §6.2、07 M2
- 時期: M2

### M6. 宣言的 UI と関数の受け渡し
- 経緯: M3 で mod の UI ツリーを Worker から UI スレッドに渡すとき、`onClick` などの関数と `Reactive`（getter）、`Signal` は postMessage で送れない
- 選択肢: UI スレッド側で mod のコードを評価する / **サンドボックス側でツリーを平らにして送る** / 関数を文字列化して送る
- 決定（2026-10-11）: **サンドボックス側で解決する**。SDK（`sdk.js`）が描画のたびに getter を評価し、`LocalizedString` を現在の言語に解決し、関数を `{ $fn: id }`、Signal を `{ $sig: id, value }` に置き換えた JSON を送る。UI はクリックや入力を id で返し、SDK が元の関数を呼ぶ。Signal の `set()` か `ctx.ui.refresh()` で mod の全ツリーを描き直す（依存追跡はしない。v1 のツリーは小さい）。古い描画の id は 3 世代残し、描画直後のクリックが迷子にならないようにする
- 根拠: mod のコードが UI スレッドに触れないことが隔離の前提（判断 C2）。関数の文字列化は閉包を失う
- 影響: 05 §5.3、packages/ui/src/mods/tree.ts
- 時期: M3

### M7. 公式でない mod の既定と、無効化の記録
- 経緯: 05 §4 は「有効／無効の切替」を言うが、どこに記録するかと、入れただけの mod が動くかは決めていなかった
- 決定（2026-10-11）: `config.toml` の `[mods] enabled / disabled`（06 §2 のとおり）。`disabled` にあれば無効、`enabled` にあれば有効、どちらにもなければ **`otterm.*` だけ有効、それ以外は無効**。承認画面で「やめる」を選ぶと `disabled` に書き、次回から聞かない。3 回続けて落ちた mod も `disabled` に書く
- 根拠: フォルダに置いただけ（または `pnpm dev` でリンクしただけ）で動き出すより、`otterm mod enable` か一覧パネルで明示的に有効にする方が、D6 の「clone しただけで動かない」と同じ姿勢になる
- 影響: 05 §4、06 §2
- 時期: M3

### M8. 同梱 mod の権限承認
- 経緯: M4 で同梱 mod（7 つの extension と辞書）を入れた。05 §6.1 は「ユーザーが承認」だが、初回起動で 7 回の承認画面を出すわけにはいかない
- 決定（2026-10-11）: **otterm に同梱された mod は承認済みとして扱う**（`bundled = true`）。無効化はできるが削除はできない（`otterm mod remove` は拒否）。ユーザーが同じ id の mod を `mods/` に入れると、そちらが同梱版を隠す（更新やフォーク用）。同梱 mod の実体は `build.rs` が実行ファイルに埋め込み、起動時に `<データ>/bundled-mods/<id>/` へ書き出す（内容のハッシュが変わったときだけ）
- 根拠: 同梱 mod は本体と同じ配布物で、同じ署名の下にある。承認画面は「他人の mod を入れる」ための仕組み
- 影響: 05 §4、§9
- 時期: M4

### M9. 入力行の取得の実装順
- 経緯: 02 §6 は「方式 A（シェル統合から `7777;line`）を主、B（画面からの推定）をフォールバック」とした。M4 で調べると、A を 1 キーごとに出せるのは zsh（`zle-line-pre-redraw`）だけで、bash の readline、fish、PSReadLine には行の変化を知らせるフックがない
- 決定（2026-10-11）: **まず B を Rust に実装する**。`otterm-vt` が `133;B` の位置を覚え、そこからカーソル行（折り返し含む）までを読む。フレームのたびに比べ、変わったときだけ `Input` イベントを出す。A は zsh だけ後から足し、`exact` で区別する
- 根拠: B はシェルを選ばず、PSReadLine の予測表示（薄い文字）もそのまま読めてしまう欠点はあるが、説明・危険判定・補完の入力としては十分だった。A を待つと pwsh（初心者の中心）で支援が動かない
- 影響: 02 §6、03 §8.0
- 時期: M4

### M11. `OSC 7777;line` の形
- 経緯: 03 §6.1 は `OSC 7777;line;<base64>` としていたが、zsh には base64 の組み込みがなく、1 キーごとに `base64` を fork すると入力が重くなる
- 決定（2026-10-11）: **`OSC 7777;line;<cursor>;<%エンコード>`**。%エンコードは zsh の中だけで書け（既存の `__otterm_urlencode`）、fork が要らない。カーソルは文字単位（zsh の `$CURSOR`）。行が変わらないときは送らない
- 影響: 03 §6.1、02 §6
- 時期: M4

### M10. 履歴 UI と `otterm.history-search`
- 経緯: 05 §9 は履歴 UI を同梱 mod `otterm.history-search` としているが、`@otterm/api` に履歴を読む名前空間がなく、SQLite はブローカーの外にある
- 決定（2026-10-11）: v1.0 では **履歴 UI は本体が描く**（`Ctrl+R`、パレットと同じ部品）。実行記録は Rust の `history.sqlite`。mod から履歴を読む API（`ctx.history`）は v1.x で検討し、そのとき mod に切り出す
- 影響: 03 §8.5、05 §9
- 時期: M4

### M12. パネルの表示切替キー
- 経緯: 06 §5.2 は `sidebar.left.toggle` を `ctrl+b`、`panel.bottom.toggle` を `ctrl+j` としていたが、M5 で実装すると、どちらもシェルが使うキーだった（readline の 1 文字戻る、改行）。otterm のキーバインドには「入力待ちのときだけ」の条件がまだなく、奪うと bash / zsh の操作が壊れる
- 決定（2026-10-11）: Windows / Linux は **`ctrl+shift+b`（左）、`ctrl+alt+b`（右）、`ctrl+shift+j`（下）**。macOS は 06 §5.2.1 のまま `cmd+b` / `cmd+shift+b` / `cmd+j`。あわせて領域間のフォーカス移動 `F6` / `Shift+F6`（`focus.next_region` / `focus.prev_region`）を足した（04 §5 のキーボード完結）
- 根拠: Ctrl+Shift と Cmd の組み合わせは TUI もシェルもほぼ使わない（代替画面でも otterm が使う「強い」キー、06 §5.3）
- 影響: 06 §5.2
- 時期: M5

### M13. テーマを選んだときの OS 追従
- 経緯: `appearance.follow_system = true`（既定）のとき、ライトモードの OS でダークテーマのカードを押しても `appearance.theme`（ダーク用）が変わるだけで、画面は何も変わらない
- 決定（2026-10-11）: **OS の今のモードに合うテーマは、そのモードの枠（`theme` か `theme_light`）に入れる。合わないテーマを選んだら `theme` に入れて `follow_system` を切る**。設定画面のカードは「押せばそのテーマになる」
- 根拠: 押しても変わらないボタンは壊れて見える。追従に戻すのは外観の項目 1 つ
- 影響: 04 §2.5、§6
- 時期: M5

### M14. 透過・背景画像の描き方
- 経緯: `appearance.window.opacity` と背景画像（04 §2.1）には透過ウィンドウが要るが、Tauri の `transparent` はウィンドウ作成時にしか決められない。また、ターミナルの既定背景と画面の背景の両方に不透明度を掛けると色が重なって濃くなる
- 決定（2026-10-11）: **ウィンドウは常に `transparent: true` で作り（macOS は `macOSPrivateApi`）、既定は不透過の背景を塗る**（判断 I6 の見た目は変わらない）。透過・背景画像のときは **色を持つ層を 1 枚だけ**にする: ウィンドウ（`html`）がテーマ背景（`opacity` の分）と画像と画像を薄める幕を持ち、ターミナルは既定背景を描かない（WebGL / Canvas 2D とも既定背景のアルファを 0 に）。ぼかしは OS の効果（Windows は Acrylic、macOS は UnderWindowBackground）で、`opacity < 1` のときだけ。背景画像は `<設定>/backgrounds/` にコピーして相対パスで持つ
- 根拠: 層が 1 枚なら不透明度の値がそのまま見た目になる。画像をコピーしておけば設定フォルダごと持ち運べる
- 影響: 04 §2.1、06 §2
- 時期: M5

### M15. テーマ mod と設定画面の書き戻し
- 経緯: 05 §2 の `theme` kind の mod をどう有効にするか、設定画面がどのキーを書き換えてよいかを決めていなかった
- 決定（2026-10-11）: **`theme` kind の mod は入れた時点でテーマ一覧に出る**（`[mods] disabled` にあれば出ない）。コードも権限もないので承認画面を出さない。同名ならユーザーの `<設定>/themes/*.toml` が勝つ。設定画面は **`config.toml` の任意のキーを 1 つずつ書く**（`config_write`、toml_edit でコメントと順序を保つ）。書いた後の内容を読み直し、そのキーの節に新しい警告が出るなら書かずに拒否する。mod からの `ctx.settings.host.set` は従来どおり許可リストのキーだけ
- 根拠: テーマは見た目だけで、悪用できる経路がない。設定画面はユーザー自身の操作なので許可リストは要らないが、壊れた値をファイルに残さない
- 影響: 05 §2、§4、06 §3
- 時期: M5

### M16. UI のアイコン
- 経緯: mod は Lucide の名前でアイコンを指定する（`icon: "folder"`）が、M3 では数個の記号に置き換えるだけで、知らない名前は「•」になっていた。ファイルツリーやパネルのタブ、ステータスバーで目立つ
- 選択肢: Lucide を同梱する / 同梱の Symbols Nerd Font の字形に対応させる / **自前で描く**
- 決定（2026-10-11）: **otterm が描いた SVG のアイコン集**（`packages/ui/src/icons.tsx`、77 個）。名前と描き方（24px 格子、線幅 2、丸い端）は Lucide に合わせ、絵は自前。知らない名前は小さな丸。絵文字はアイコンに使わない
- 根拠: 依存とライセンス表示が増えない。フォントの字形は名前との対応表が大きく、線の太さが揃わない。SVG は `currentColor` でテーマに従う
- 影響: 05 §5.3、12 §5
- 時期: M5

### M17. セーフモードの入り方
- 経緯: 04 §2.3 は「起動時 `Shift` 押下でセーフモード」としていた。Rust から押されているキーを読むには OS の API（Windows は `GetAsyncKeyState`）を `unsafe` で呼ぶか依存を足す必要があり、ワークスペースは `unsafe_code = "deny"`
- 決定（2026-10-11）: **`otterm --safe-mode` と、コマンドパレット・設定 › 詳細の「セーフモードで再起動」**。セーフモードでは同梱の既定テーマ（otterm Dark / Light）、テーマと user.css の CSS なし、透過・背景画像・ぼかしなし、mod を起動しない。上部の帯に「通常モードで再起動」。再起動は同じ引数で新しいプロセスを起こし、今のプロセスを閉じる（実行中のプログラムがあれば確認）。`Shift` 押下は見送り
- 根拠: CSS で画面が壊れても、パレット（`Ctrl+Shift+P`）か別の端末からの `otterm --safe-mode` で入れる。`unsafe` を入れる理由としては弱い
- 影響: 04 §2.3、06 §4、07 M6
- 時期: M5

### M18. 費用をかけない配布
- 経緯: M6 の計画（A9、C10）には有料の証明書と CI が前提の項目がある。メンテナの方針は「お金のかかることは一切しない」（2026-10-11）で、リポジトリは private
- 決定（2026-10-12）: **Windows・macOS のコード署名はしない。ビルドは各 OS の手元で `scripts/release.mjs`、公開は手作業。** updater の署名（minisign、無料）は行う。GitHub Actions のリリース用ワークフローは手動実行のみで、private のうちは実行しない。mod の配布物は sigstore（D2）の代わりにレジストリのインデックスの SHA-256 で検証する（レジストリが public になって Actions が無料になったら D2 に戻す）
- 影響: 初回起動で SmartScreen / Gatekeeper の警告が出る。Homebrew は自前の tap で配る。詳しくは [release.md](release.md) §6
- 時期: M6

### M19. コンソール向けの `otterm.com`
- 経緯: Windows のリリース版は GUI プログラムで、`otterm config get` の出力がコンソールに出ない。`AttachConsole` には `unsafe` が要り（M17 で避けた）、付けても cmd や PowerShell は終了を待たない
- 決定（2026-10-11）: **`otterm.exe` の隣に小さなコンソールプログラム `otterm.com`**（`crates/otterm-console`）。`PATHEXT` で `.COM` が先に見つかる。サブコマンドは出力をパイプで中継し、終了コードを返す
- 影響: 06 §4、release.md
- 時期: M6

### M20. ストアの接続確認とクラッシュログの扱い
- 決定（2026-10-12）: ストア画面は初めて開いたときに「レジストリに接続する」を押すまで接続しない（K5 の具体化。答えは `state/registry-consent`）。CLI の `otterm mod search|install|update` は利用者の明示的な操作なので確認しない。クラッシュログは「Issue を作る」でクリップボードにコピーし、Issue の URL には入れない（パスにユーザー名が入りうるため、利用者が中身を見てから貼る）
- 影響: 05 §7.2、C11
- 時期: M6

### M21. コツメ本体の置き場所
- 経緯: 08 §6.2 は「コツメ自体は同梱 mod `otterm.mascot` として実装し、他の mod と同じ API を使う」とする。mod は Worker の中で動き、DOM にも他の mod のイベントにも触れられないので、描画・表情の判断・吹き出しのキューを mod に置くと、ホストとの往復が増え、危険確認などホスト側の出来事を拾えない
- 決定（2026-10-12）: **描画と状態（MascotStore、表情の判断、吹き出しのキュー）はホストの UI に置く。** mod からは `ctx.mascot`（say・setMood・reactions・outfits）で同じことができる。反応ルールの `when` は mod 自身の関数なので、その mod の Worker で評価する。台詞を出すかはホストがガイドレベルと設定で決め、出さないときはトーストに置き換える
- 影響: 08 §6.2、05
- 時期: M4.5

### M22. AI のどこまでをコアに置くか
- 経緯: 10 §5 は「コアには AI の知識を一切置かない」とする。一方で API キーを mod の JavaScript に渡すと、サンドボックスの外に出やすい。送信前のプレビューと自動マスクも、mod 任せでは保証できない
- 決定（2026-10-12）: **プロバイダへの通信、キーチェーン、自動マスク、ログ、頻度制限、プレビューはホスト（`ai.rs` と UI）に置く。** 質問の作り方、回答の形、画面は `otterm.ai-assist` に置く。ホストはプロンプトを持たない。`otterm.ai-assist` は `[ai] enabled` が真のときだけ起動し、消しても他の機能は何も変わらない
- 影響: 10 §5、§7
- 時期: M5.5

### M23. レジストリの署名

- 背景: D2 は sigstore のキーレス署名（GitHub Actions から公開）だった。M18 で、お金をかけない間はインデックスの SHA-256 だけで配布物を検証することにした。リポジトリは public になったが、ワークフローは手動実行のままにしている
- 決定（2026-10-12）: **インデックス（`registry/index.json`）にメンテナの minisign 鍵で署名する**。updater と同じ形式（`tauri signer sign`、無料、オフライン）。クライアントは `index.json.sig` を本体に埋め込んだ公開鍵（`registry/registry-key.pub`）で検証し、既定のレジストリでは署名が必須。インデックスは各配布物の `sha256` とサイズを持つので、配布物もこの署名で守られる
- ユーザーが `[mods] registry` で設定した別のレジストリは署名なしを許す（ストアと `otterm mod search` に「署名なし」と出す）。署名があって合わないときは拒否する
- 鍵: `~/.tauri/otterm-registry.key`（updater とは別の鍵。鍵 ID `2736B83507A3D2B7`）。リポジトリには入れない。ローテーションは公開鍵を差し替えた版を出してから新しい鍵で署名し直す（古い版は新しい鍵の署名を拒むので、切り替えの前に新しい公開鍵の入った版が行き渡っている必要がある）
- sigstore（作者ごとの署名）は、公開を GitHub Actions に移すときに改めて検討する

### M24. シェルを素の状態で起動する

- 背景: これまでは PowerShell のプロファイルや `~/.bashrc` を読んだうえで otterm のフックを足していた（B6）。そのため、ほかのターミナル用に入れた機能（プロンプトのテーマ、PSReadLine の拡張など）が otterm にも入り、otterm の見た目や挙動がユーザーの環境しだいで変わっていた
- 決定（2026-10-12）: **既定では、シェル自身の設定ファイルを読まずに起動する**（`shell.user_startup_files = false`）。otterm は「インストールしたままのシェル + otterm の連携」から始まり、便利な機能は設定と mod で足す。読みたい人は設定でオンにする
- 具体的には PowerShell は `-NoProfile`、cmd は `/D`（AutoRun を読まない）、bash と zsh は otterm のフックがユーザーのファイルを読まない（`/etc` の全体設定は読む）、fish は `--no-config`。連携をオフにしたときも、シェルのフラグで同じようにする
- インストーラ: ユーザー単位の既定のインストール先を `%LOCALAPPDATA%\Programs\otterm` にした。Tauri の既定（`%LOCALAPPDATA%\otterm`）は otterm のデータフォルダと同じで、プログラムとデータが混ざっていた。Tauri に設定がないため、NSIS のテンプレートを写して 1 行変えている（`crates/otterm-app/windows/installer.nsi`）

### M25. 何も入っていない状態から始める

- 経緯: 1.0 は公式の同梱 mod を既定でオンにしていた。コツメ、`Ctrl+R` の履歴、`Shift+Enter` の複数行エディタ、otterm のプロンプトバーはコアに直接あり、mod の一覧から外せなかった。上級者には「入れた瞬間から otterm の流儀」になり、ほかのターミナルから移りにくかった
- 決定（2026-10-12）: **1.1 から、すべての mod を既定でオフにする。** 入れたばかりの otterm は、ほかのターミナルとほとんど変わらない。コアにある機能のうち、外せるものは kind `feature` の同梱 mod（`otterm.mascot`、`otterm.history-search`、`otterm.multiline-editor`、`otterm.prompt-bar`）をスイッチにする。描画と状態はホストに置いたまま（M21）で、mod がオフのあいだキーはシェルに届き、プロンプトはシェル自身のものになる。補完の `Ctrl+Space` も `otterm.completion` がオンのときだけ奪う
- 補足: mod をオンにすると `[dependencies]` もオンになる（補完などは辞書を連れてくる）。AI の mod は `[ai] enabled` も立てる。mod の一覧に「おすすめをまとめてオンにする」を置く。1.0 から更新した環境は、初回起動時に 1.0 で既定オンだった mod を `[mods] enabled` に書き込み（ユーザーがオフにしたものは除く）、今までどおり使える。済んだ印はデータフォルダの `mods-start-off`
- 影響: 05 §2、§9、08 §6.2、03 §8.5、§8.6、§11
- 時期: 1.1

### M26. シェルをウィンドウとは別のプロセスで動かす

- 経緯: ほかのターミナルとの差を調べた（[13-positioning.md](13-positioning.md)）。アプリが落ちたり更新したりしても、tmux なしでシェルとスクロールバックが残るターミナルは、調べた範囲にない。Windows には tmux がない。02 §2.1 は v1.x でデーモンを分けると予定していた
- 決定（2026-10-12）: **PTY と VT の状態をセッションデーモン（`otterm --daemon`）に置く。** ウィンドウは `RemoteSessionManager`（`otterm-session/src/remote.rs`）で `SessionManager` trait 越しに話すので、上の層は変わらない。通信は 127.0.0.1 の TCP 1 本で、データフォルダにしか置かないトークンで認証する（画面のソケットと同じ考え方、M2）。要求・応答・イベントは JSON、フレームは diff.rs のバイト列をそのまま送る
- 残す条件: `general.keep_sessions`。`on-crash`（既定）はクラッシュと再起動（更新、設定の反映）で残し、普通に閉じたら終える。`always` は閉じても残し、次のウィンドウがつなぎ直す。`never` は今までどおりウィンドウの中で動かす。デーモンが起動できないときも、ウィンドウの中で動かす
- 更新: Windows では、デーモンはデータフォルダにコピーした実行ファイル（`<data>/daemon/bin/<ビルド>/otterm-daemon.exe`、同梱の ConPTY も一緒）から動く。インストーラが `otterm.exe` を置き換えても止まらない。デーモンはビルドごとに分かれ、新しいウィンドウは新しいセッションを自分のビルドのデーモンで始め、古いデーモンに残ったシェルもつなぎ直す。シェルがなくなりウィンドウもないデーモンは 10 秒で終わる
- セッション id はデーモンごとに `(pid の下位 16 ビット) << 16` から数える。フレームは id を u32 で運ぶため
- 時期: 1.2
