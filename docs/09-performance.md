# 09. 性能戦略（Performance）

## 1. 目標の置き方

正直な前提から始める。WebView を経由する otterm が、ネイティブ GPU 描画の Ghostty や WezTerm を **素の速さで上回ることは難しい**。
狙うのは「上回る」ではなく「**体感で区別がつかない**」こと。具体的には次の 3 つ。

1. 打鍵から表示までの遅延が、同じマシンで測った Ghostty との差 **1 フレーム（16 ms）以内**
2. 大量出力のスループットで Windows Terminal を下回らない
3. 「otterm らしい機能（ラコ、入力支援、mod）を全部オンにしても」上の 2 つが崩れない

3 つ目が otterm 固有の難しさであり、同時に差別化でもある。Warp は機能を足した結果重くなった。otterm は「親切さは速さの上に乗せる」を設計で保証する。

## 2. 遅延はどこで生まれるか

打鍵 1 回が画面に出るまでの経路と、各段の予算。

| 段 | 処理 | 予算 | 方針 |
| --- | --- | --- | --- |
| 1 | OS キーイベント → WebView → JS | 1〜2 ms | WebView 固有。ここは削れない |
| 2 | JS → Rust（IPC）→ PTY 書き込み | < 1 ms | **mod を通さない**。キー入力は Rust に直行し、入力支援はコピーを非同期で受け取る |
| 3 | シェルのエコー → PTY 読み取り → VT 解析 → グリッド更新 | < 1 ms | セッションごとに専用スレッド。解析は Rust で同期的に |
| 4 | グリッド差分 → WebView へ転送 | 1〜2 ms | バイナリ差分。JSON を使わない。変更セルのみ送る |
| 5 | WebGL 描画 → コンポジタ → 表示 | 1 フレーム + α | ダメージ領域のみ再描画。ラコや UI のアニメーションはターミナル描画と別レイヤ |

合計の目標は p99 16 ms 以下、p50 8 ms 以下。段 5 の「+ α」が WebView のコンポジタ待ちで、ここがネイティブとの差になる。

## 3. 設計上の決定

### 3.1 入力経路に何も挟まない

- キー入力は UI スレッドから Rust コアへ直送し、PTY に書く。**mod の `onInputChange` や説明生成は、その後に非同期で配られるスナップショット** に対して動く
- `before-execute` だけは Enter を止める必要があるため同期的に待つが、タイムアウト 50 ms。超えた mod は無視して実行し、警告を出す
- IME 変換中の文字列はシェルに送らない（確定時のみ）。日本語入力でカーソルが暴れない

### 3.2 出力は「フレーム単位でまとめる」

- PTY からの読み取りは可能な限り大きなバッファで行い、VT 解析はスレッドをブロックせずに進める
- 描画は最大 60 fps（可変リフレッシュ対応時は 120 fps）に制限し、1 フレームの間に届いた出力はまとめて 1 回の差分にする。`cat` で 100 MB 流しても描画回数は秒間 60 回を超えない
- 画面外（スクロールバックに流れる行）は描画せずにインデックスだけ更新する

### 3.3 グリッド転送

| 方式 | 内容 | 判定 |
| --- | --- | --- |
| JSON over IPC | 簡単だが 1 画面 80×24 で数十 KB、シリアライズに数 ms | 不採用 |
| **バイナリ差分 over Tauri raw IPC** | 変更セルを `(row, col, len, cells...)` のバイナリで送る。Tauri 2 の生ペイロードで JSON を回避 | **v1.0 採用** |
| 共有メモリ | Rust と WebView で同じバッファを見る。コピーゼロ | WebView の制約で現状は困難。ネイティブレンダラ移行時に自然に実現 |

M0 でバイナリ差分を実測し、段 4 が 2 ms に収まることを確認する。

### 3.4 レンダラは差し替え可能にする

```
trait Renderer {
    fn attach(&mut self, surface: Surface);
    fn apply_diff(&mut self, diff: &GridDiff);
    fn present(&mut self);
    fn set_font(&mut self, font: &FontConfig);
    fn hit_test(&self, x: f32, y: f32) -> Option<CellPos>;
}
```

| バックエンド | 実装 | 時期 |
| --- | --- | --- |
| `webgl` | WebView 内の WebGL2 / WebGPU。グリフアトラスをテクスチャに持つ | v1.0 |
| `native-wgpu` | ターミナル領域だけを **ネイティブの子サーフェス** に wgpu で描く。タブバーやパネルなど UI は WebView のまま。入力もネイティブ側で受けて Rust へ直行 | v1.x（M0 の判定次第で前倒し） |

ネイティブ化すれば段 1、4、5 がすべて縮む。WebView の上にネイティブサーフェスを重ねる構成は OS ごとに癖があり（Windows の透過、macOS のレイヤ順、Linux Wayland のサブサーフェス）、v1.0 でそこに時間を使わないために WebGL から始める。ただし **グリッドとレンダラの境界は最初から trait で切り、UI 側は「ターミナル領域は差し替わるもの」として作る**。

### 3.5 VT コアの選択肢

| 選択肢 | 長所 | 短所 |
| --- | --- | --- |
| Rust 自前（`vte` クレート + 自作グリッド） | Rust コアと一体。改造自由 | 互換性の作り込みに時間がかかる |
| `alacritty_terminal` クレート | 実績あり、高速 | API が Alacritty 都合。ブロックや画像の拡張がしづらい |
| libghostty（Ghostty のコアを C ライブラリ化したもの） | Ghostty と同じ VT 互換性と速度 | Zig 製で Rust からは FFI。API がまだ安定していない。ブロック用の OSC 拡張を足すのが難しい |

**v1.0 は Rust 自前（`vte` 土台）** とし、互換テストで Ghostty / WezTerm と同じコーパスを通す。libghostty は M0 で動作とライセンスを確認し、互換性で追いつけない場合の代替として記録しておく。

### 3.6 起動時間

- 設定はパース済みのバイナリキャッシュを持ち、TOML の変更がなければそれを読む
- グリフアトラスはディスクにキャッシュし、フォントが同じなら再生成しない
- mod は **遅延ロード**。`activate` は最初のタブが描画された後に走らせる。ラコも例外ではない（最初の 1 フレームには出ない）
- 目標: コールドスタート 500 ms（mod なし）、1 秒（同梱 mod あり）

### 3.7 メモリ

- スクロールバックは 1,024 行ごとのチャンクに分け、画面から遠いチャンクは圧縮（LZ4）して保持。さらに遠いものはディスクへ
- グリフアトラスは LRU で上限 64 MB
- mod の Worker は無操作 10 分でサスペンド（状態は保存）。イベントが来たら再開
- タブ数に上限は設けない。合計メモリが 1 GB を超えたらステータスバーに警告を出し、大きいスクロールバックを持つタブを示す（判断 I13）

### 3.8 ラコと UI を「ターミナルの邪魔をしない」層に置く

- ラコのアニメーションは `transform` と `opacity` のみ（コンポジタで完結し、レイアウトを起こさない）
- 吹き出しの表示でターミナル領域のサイズを変えない（リフローが PTY のリサイズを起こすため）。吹き出しは常にオーバーレイ
- 入力支援バーの高さは固定。内容が変わっても高さが変わらない
- 大量出力中（秒間 1 MB 超）はラコの表情更新を止める。出力が落ち着いてから追いつく

## 4. 計測と回帰防止

### 4.1 ベンチマーク一式（`tests/bench/`）

| 名前 | 測るもの | 方法 |
| --- | --- | --- |
| `typing-latency` | 打鍵 → 描画完了 | 合成キーイベントの発行時刻と、該当セルが描画されたフレームの完了コールバックの差。1,000 回で p50 / p99 |
| `throughput` | 大量出力 | 100 MB テキストの `cat`、`yes` の 10 秒、vtebench 相当のシナリオ |
| `startup` | 起動 | プロセス開始からプロンプト表示まで。コールド／ウォーム |
| `memory` | 常駐メモリ | 1 セッション、10 セッション、スクロールバック満杯 |
| `mod-overhead` | mod の影響 | 同梱 mod を全部オン／全部オフで `typing-latency` を比較 |
| `resize` | リサイズの追従 | ウィンドウを 100 回リサイズしてフレーム落ち数 |

### 4.2 比較対象の実測

M0 の時点で、**同じマシン・同じフォント・同じシェル** で Ghostty、WezTerm、Windows Terminal、Alacritty を同じ手順で測り、基準値を `docs/bench/baseline.md` に記録する。他社の公称値は使わない。

### 4.3 CI ゲート

- `typing-latency` の p99 が基準から 10 % 悪化したら CI を落とす
- `startup` が 20 % 悪化したら落とす
- 各 PR にベンチ結果の差分をコメントする

### 4.4 M0 での判定基準

| WebGL 経路の p99（参照マシン） | 判断 |
| --- | --- |
| 16 ms 以下 | 計画通り。ネイティブレンダラは v1.x |
| 16〜25 ms | WebGL のまま進めつつ、M3 と並行でネイティブレンダラの試作を始める |
| 25 ms 超 | ネイティブレンダラを v1.0 に前倒し。M1 の見積もりを +4 週 |

## 5. 「速さ」は otterm の方向性と合うか

合う。むしろ前提になる。

- 初心者にとって「打ったのに反応が遅い」は、エラーより先に不信感を生む。親切な UI は速さの上にしか成立しない
- 上級者が乗り換えを検討する最初の関門が速さ。ここで落ちると mod もラコも見てもらえない
- Warp が証明したのは「機能を足すと重くなる」こと。otterm は「足しても重くならない設計」を売りにできる。それが 3.1 と 3.8 の意味

一方で、Ghostty の「ネイティブであること自体の美しさ」とは競わない。otterm の見た目の強みは改造の自由度にあり、そのために WebView を選んでいる。速さは「区別がつかない」まで持っていき、それ以上は追わない。
